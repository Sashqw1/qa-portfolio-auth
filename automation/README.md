# Автотесты

Автотесты живут в репозитории самого продукта — так они запускаются рядом с
кодом и ломаются вместе с ним:

**[github.com/Sashqw1/Sashqw1-robocalc, ветка `qa/tests`](https://github.com/Sashqw1/Sashqw1-robocalc/tree/qa/tests/frontend/src)**

| Файл | Что проверяет |
|---|---|
| `src/features/wizard/mockEconomics.test.ts` | Расчёт экономики: базовый сценарий, CAPEX и окупаемость, граничные случаи (пустой состав оборудования, нулевая стоимость персонала), анализ чувствительности |
| `src/shared/ui/NumberField.test.tsx` | Числовое поле формы: ввод целых и дробных чисел, поведение при недопустимых символах и нечисловых форматах |

## Стек

- **Vitest 5** — модульные тесты расчётной логики.
- **Testing Library + jsdom** — компонентные тесты полей ввода: взаимодействие
  описывается так же, как его выполняет пользователь (`userEvent.type`), а не
  через внутренние методы компонента.

## Запуск

```bash
cd frontend
npm install
npm test          # разовый прогон
npm run test:watch
```

## Результат прогона

```
 Test Files  2 passed (2)
      Tests  9 passed | 4 expected fail (13)
```

Четыре теста помечены как `it.fails` — они **должны** падать, потому что
фиксируют подтверждённые дефекты:

| Тест | Дефект |
|---|---|
| «без выбранного оборудования расчёт не падает и не обещает экономии» | [BUG-001](../bugs/BUG-001.md) |
| «ROI не принимает фиктивное значение при нулевом CAPEX» | [BUG-002](../bugs/BUG-002.md) |
| «при вводе текста поле и данные не расходятся» | [BUG-004](../bugs/BUG-004.md) |
| «не принимает шестнадцатеричную запись как число» | [BUG-005](../bugs/BUG-005.md) |

Такая разметка решает две задачи: прогон остаётся зелёным и годится для CI,
а когда дефект починят, тест просигналит об этом — `it.fails` падает, если
проверка внезапно начинает проходить. Получается регрессионный маркер,
который нельзя забыть снять.

## Как собирались доказательства для отчётов о дефектах

Снимки экрана сделаны headless-браузером Edge по списку адресов стенда
в двух разрешениях — скрипт `capture.sh` обходит 13 экранов и складывает
результат в каталог. Это позволило за один прогон сравнить целевое
разрешение 1366×768 с контрольным 375×667 и приложить к [BUG-007](../bugs/BUG-007.md)
два снимка одного и того же экрана.
