# BUG-005. Числовое поле принимает шестнадцатеричную и научную запись

| Поле | Значение |
|---|---|
| Серьёзность | Minor |
| Приоритет | Low |
| Компонент | Общий компонент формы `NumberField` (`shared/ui/Field.tsx:124`) |
| Окружение | https://sashqw1.github.io/Sashqw1-robocalc/, Edge 141, Windows 11 |
| Статус | Открыт |
| Найден | Компонентный автотест `NumberField.test.tsx` |

## Описание

Для разбора ввода используется `Number(...)`, который понимает не только десятичные
числа, но и шестнадцатеричную (`0x10`), восьмеричную (`0o20`), двоичную (`0b101`)
и научную (`1e5`) запись. В полях вроде площади объекта или численности персонала
такие форматы бессмысленны, но принимаются молча и пересчитываются.

## Шаги воспроизведения

1. Открыть шаг 2 «Параметры объекта».
2. В поле «Площадь объекта» ввести `0x10`.
3. Посмотреть, какое значение ушло в данные формы.

Компонентный автотест:

```tsx
await userEvent.type(input, '0x10');
expect(lastValue).not.toBe(16);
```

## Фактический результат

```
AssertionError: «0x10» интерпретировано как число 16: expected 16 not to be 16
```

Введено `0x10` — в расчёт ушло 16. Аналогично `1e5` превращается в 100 000.

## Ожидаемый результат

Принимаются только десятичные числа с запятой или точкой в качестве разделителя.
Остальные записи отклоняются с подсказкой о допустимом формате.

## Влияние

Самостоятельно пользователь такие значения вводит редко, но они могут попасть
при вставке из буфера обмена или при импорте данных из внешнего файла.
Опасна молчаливость: подстановки не видно, значение выглядит обычным числом.

## Рекомендация

Разбирать ввод строгим выражением для десятичных чисел, например
`/^-?\d+([.,]\d+)?$/`, вместо `Number(...)`.
