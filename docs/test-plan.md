# Тест-план: веб-сервис ROBOCALC

## 1. Объект тестирования

ROBOCALC — веб-сервис подбора роботизированных решений и расчёта экономического
эффекта для склада, аэропорта и медицинского учреждения. Пользователь проходит
визард из восьми шагов, получает подбор техники из каталога, расчёт CAPEX/OPEX/TCO,
сравнение сценариев финансирования и итоговый отчёт.

| Параметр | Значение |
|---|---|
| Стенд | https://sashqw1.github.io/Sashqw1-robocalc/ |
| Репозиторий | https://github.com/Sashqw1/Sashqw1-robocalc |
| Версия на момент тестирования | сборка от 25.09.2026 |
| Технологии | React 19, TypeScript, Vite; данные — моки на стороне клиента |
| Карта экранов | https://sashqw1.github.io/Sashqw1-robocalc/screen-map.html |

Сервис находится в стадии прототипа: бэкенда нет, данные каталога и расчёты
выполняются на клиенте. Это влияет на объём тестирования — см. раздел 6.

## 2. Цель тестирования

Проверить, что заявленная функциональность работает по описанию, а расчётные
значения, которые пользователь увидит в отчёте, достоверны и непротиворечивы.
Отдельное внимание — границам числовых полей и состояниям, в которых расчёт
теряет смысл (нет оборудования, нулевые затраты, отсутствие окупаемости).

## 3. Объём работ

### 3.1. В объёме

| Область | Что проверяется |
|---|---|
| Навигация и доступ | Маршруты всех экранов, разграничение по ролям «гость / пользователь / администратор», обработка несуществующих адресов |
| Визард, шаги 1–8 | Переходы между шагами, сохранение черновика, блокировка «Далее» при ошибках |
| Формы параметров | Обязательность, границы значений, целочисленность, формат габаритов, межполевые правила |
| Расчёт экономики | CAPEX, OPEX, годовой эффект, срок окупаемости, ROI, TCO, анализ чувствительности |
| Подбор и сравнение | Фильтрация каталога, статусы совместимости, формирование состава оборудования |
| Отчёт и экспорт | Итоговый дашборд, печатная форма отчёта |
| Интерфейс | Светлая и тёмная темы, рабочее разрешение от 1366×768, поведение на меньших экранах |

### 3.2. Вне объёма

- Нагрузочное тестирование и тестирование безопасности — бэкенда нет, нагружать нечего.
- Интеграционное тестирование с реальным API — на стенде работают моки.
- Тестирование 2D-редактора плана и симуляции — на момент работы это заглушки.
- Мобильные разрешения как целевые: по нефункциональным требованиям заявлена
  работа от 1366×768, меньшие экраны проверялись только на наличие явных дефектов.

## 4. Подход

Применяются техники тест-дизайна:

- **Классы эквивалентности и граничные значения** — числовые поля форм
  (площадь, численность персонала, стоимость, горизонт расчёта).
- **Таблица решений** — доступность шагов визарда в зависимости от роли и
  заполненности предыдущих шагов.
- **Переходы состояний** — черновик → рассчитан → изменены параметры → требуется пересчёт.
- **Попарное тестирование** — сочетания «тип объекта × способ финансирования × состав оборудования».
- **Исследовательское тестирование** — свободный проход по сценариям с фиксацией аномалий.

Уровни:

1. **Модульные и компонентные автотесты** (Vitest, Testing Library) — расчёт
   экономики и поведение полей ввода. Код: ветка `qa/tests` репозитория продукта.
2. **Ручное функциональное тестирование** по тест-кейсам — сценарии визарда.
3. **Проверка интерфейса** — скриншотное сравнение экранов в разрешениях
   1366×768 и 375×667, светлая и тёмная темы.

## 5. Критерии

**Критерии начала:** стенд доступен, карта экранов и описание шагов визарда
актуальны, роли переключаются.

**Критерии завершения:**

- выполнены все тест-кейсы высокого приоритета;
- дефектов уровня Blocker и Critical в открытом состоянии нет;
- каждый найденный дефект воспроизведён повторно и описан с шагами;
- автотесты проходят, известные дефекты помечены и отслеживаются.

**Критерии приостановки:** стенд недоступен более часа либо выявлен дефект,
блокирующий прохождение визарда целиком.

## 6. Риски

| Риск | Влияние | Что делаем |
|---|---|---|
| Расчёты выполняются моком на клиенте | Значения могут быть правдоподобными, но неверными | Проверяем формулы автотестами на граничных данных, а не только глазами |
| Нет бэкенда и базы | Невозможно проверить сохранение между сессиями | Ограничиваем объём, фиксируем в разделе «вне объёма» |
| Единственное окружение — GitHub Pages | Нельзя проверить поведение при ошибках сети API | Проверяем клиентскую обработку состояний загрузки и пустых данных |
| Прототип быстро меняется | Тест-кейсы устаревают | Привязываем кейсы к требованиям, а не к вёрстке |
